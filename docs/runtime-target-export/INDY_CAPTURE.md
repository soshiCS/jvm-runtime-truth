# invokedynamic Capture

## What gets captured

Every `invokedynamic` instruction that fires its bootstrap method is captured.
The primary use case is `LambdaMetafactory.metafactory` (lambda expressions), but
the hook fires for all `invokedynamic` instructions regardless of bootstrap method.

---

## Hook: `resolve_invokedynamic` in systemDictionary.cpp

**File:** `src/hotspot/share/classfile/systemDictionary.cpp`
**Lines:** ~2556 (trace_id assignment), ~2626, ~2695

The hook fires inside the indy bootstrap resolution path. At this point the
bootstrap method has been identified (from the `InvokeDynamic` CP entry) and
the `CallSite` is about to be established.

**Env var gate:** `SOROUSH_TRACE_INDY=1` enables enriched indy records. With the
gate off, a sparse `IndyCallSite` node is still created from the generated-class
side (via `indy_trace_id`), but the BSM/LMF fields are not populated.

---

## LambdaMetafactory enrichment

When the bootstrap method is `LambdaMetafactory.metafactory` (the common case
for Java lambda expressions), the system additionally captures:

- `lmf_impl_class` — the class containing the lambda body method
- `lmf_impl_method` — the synthetic method name (e.g. `lambda$main$0`)
- `lmf_impl_descriptor` — the lambda body's JVM descriptor
- `indy_name` — the functional interface method name (e.g. `"get"`, `"apply"`)
- `indy_descriptor` — the functional interface method type

These fields allow downstream consumers to directly identify the lambda body
method without parsing bytecode.

---

## `indy_trace_id` — the indy/lambda-class join key

When `invokedynamic` creates a lambda class (a hidden class generated by
`LambdaMetafactory`), the generated class also carries the same `indy_trace_id`.
This creates a join between:

- The `callsite_target` record (source: where `invokedynamic` appears)
- The `generated_class` record (the `$$Lambda/...` hidden class that was created)

The `indy_trace_id` is an increasing integer assigned at each bootstrap resolution.

---

## Output records for indy

A successful `invokedynamic` capture produces:

1. **`callsite_target`** with `category="invokedynamic"` — includes all source
   attribution + LMF fields
2. **`generated_class`** with `generated_by="LambdaMetafactory"` and matching
   `indy_trace_id` — includes the lambda class bytes

When `SOROUSH_CAPTURE_FINAL_BYTECODE=1`, a **`bytecode_artifact`** is also emitted
for the lambda class bytes (both original and post-rewrite versions if the class
was instrumented).

**Example callsite_target for a lambda:**
```json
{
  "record": "callsite_target",
  "category": "invokedynamic",
  "evidence": "OBSERVED_ONLY",
  "source_class": "RuntimeTargetShowcaseDemo",
  "source_loader_id": "0x0000000113a81990",
  "source_capture": "exact",
  "source_method": "main",
  "source_descriptor": "([Ljava/lang/String;)V",
  "source_bci": 4,
  "source_opcode": "invokedynamic",
  "source_cp_index": 0,
  "trace_id": 1,
  "indy_name": "get",
  "indy_descriptor": "()Ljava/util/function/Supplier;",
  "bootstrap_method": "java/lang/invoke/LambdaMetafactory.metafactory",
  "lmf_impl_class": "RuntimeTargetShowcaseDemo",
  "lmf_impl_method": "lambda$main$0",
  "lmf_impl_descriptor": "()Ljava/lang/Integer;"
}
```

## Non-LambdaMetafactory indy

For `invokedynamic` with other bootstrap methods (custom BSMs, `StringConcatFactory`,
`ObjectMethods`, etc.), the system captures:

- Source attribution (class, method, BCI)
- Bootstrap method reference
- `indy_name` and `indy_descriptor` from the CP entry

It does NOT attempt to reverse-engineer the `CallSite` target — that would require
understanding each BSM's semantics. The record is emitted without `lmf_impl_*`
fields.

---

## Relationship to MH capture

`invokedynamic` with `LambdaMetafactory` generates a hidden class (the lambda
body) that internally uses `MethodHandle.invoke*` calls. Those invocations are
captured separately by the MH capture system (Case A or A2 in `resolve_handle_call`).
The two capture mechanisms are independent and complementary.

---

## Known limitations

- `invokedynamic` bootstrap fires once per callsite. If the same `invokedynamic`
  instruction is executed multiple times, it fires only on the first execution.
  Subsequent invocations reuse the cached `CallSite` without firing the bootstrap.
- Non-constant `CallSite` objects (MutableCallSite, VolatileCallSite) can have
  their target changed after bootstrap. The capture records the target at bootstrap
  time only. Target mutations after bootstrap are not tracked.
- `StringConcatFactory` indy is captured structurally but not semantically
  — there is no `lmf_impl_*` enrichment for string concat.
