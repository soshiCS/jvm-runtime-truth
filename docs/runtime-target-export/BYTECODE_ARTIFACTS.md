# Bytecode Artifacts

## What gets captured

For every class loaded during the JVM run, the system optionally captures the
raw class bytes at two moments:

- **`kind="original"`** — the bytes as received before any rewriting (the classfile
  exactly as loaded from the classloader)
- **`kind="final"`** — the bytes after Phase 5 bytecode instrumentation (ENTER/EXIT
  trace injection), if the class was rewritten

**Requires:** `SOROUSH_CAPTURE_FINAL_BYTECODE=1`

---

## Hook: class load in klassFactory.cpp

**File:** `src/hotspot/share/classfile/klassFactory.cpp`
**Lines:** ~935 (bytecode capture block)

The hook fires inside `KlassFactory::create`, after the classfile bytes have been
parsed and after any bytecode transformation (Phase 5 rewriting). It captures:
1. The original (pre-rewrite) bytes via the `ClassFileStream` passed to the factory
2. The post-rewrite bytes (if Phase 5 ran) via the rewriter's output buffer

Both are fed to `soroush_graph_bytecode_artifact` (or the equivalent capture call).

---

## CRC32 cross-reference

The `crc` field on both artifact variants is the CRC32 of the class bytes. For a
`kind="final"` artifact, the `rewritten_from_crc` field contains the CRC32 of
the corresponding `kind="original"` artifact. This allows downstream tools to:

1. Match the pre-rewrite and post-rewrite versions of any class
2. Verify that the rewriter produced output for the expected input
3. Detect cases where the same original classfile was loaded under two loaders
   (different `loader_id`, same `crc`)

---

## Loader-precise identity

Both artifact variants are keyed by `(class, loader_id, crc, kind)`. Two classes
with the same name loaded under different loaders produce distinct artifact records
with distinct `loader_id` values. This correctly handles OSGi, classloader
isolation, and redefine/retransform scenarios.

---

## Rewriter interaction

When `SOROUSH_REWRITER_PHASE5_NORMAL_EXIT=1` and the class name matches the
`SOROUSH_REWRITER_PHASE5_PREFIX`, the Phase 5 rewriter runs on the class. The
`kind="final"` artifact captures the instrumented bytecode — what actually runs.

The instrumented bytecode includes:
- `ldc_w <token>; invokestatic System.soroushTraceEnter(int)` at each method entry
- `ldc_w <token>; invokestatic System.soroushTraceExit(int)` at each normal return
- Synthetic catch-all exception handler for exception-path EXIT (normal methods only, not constructors)

The `method_identity` records in the JSONL file correspond to the tokens embedded
in the `kind="final"` bytecode. If a class was NOT rewritten, no `method_identity`
records exist for it, and no `kind="final"` artifact is produced.

## Example records

```json
{"record":"bytecode_artifact","class":"RuntimeTargetShowcaseDemo","loader_id":"0x0000000113a81990","crc":"7613bd70","size":4521,"hidden":false,"kind":"original","load_kind":"load"}
{"record":"bytecode_artifact","class":"RuntimeTargetShowcaseDemo","loader_id":"0x0000000113a81990","crc":"a2b4c8d1","size":4729,"hidden":false,"kind":"final","load_kind":"load","rewritten_from_crc":"7613bd70"}
```

## Hidden class bytecode

Lambda hidden classes and other hidden classes ARE captured as bytecode artifacts:
- `hidden=true`
- `kind="original"` with the bytes as generated by `LambdaMetafactory`
- `kind="final"` if the hidden class was instrumented by the rewriter (requires
  `SOROUSH_TRACE_MH_EXEC_HIDDEN=1` — separate flag for hidden MH-internal classes;
  user lambda hidden classes are not instrumented by default because the rewriter
  skips all hidden classes)

---

## Relationship to `generated_class` records

Both `bytecode_artifact` and `generated_class` can be emitted for the same class
(e.g., a lambda class). They carry different information:

- `bytecode_artifact` — the actual bytes and their CRC; how many bytes, what kind
- `generated_class` — who created it, why, from which indy site (`indy_trace_id`)

The JSONL consumer should join them on `(class, loader_id, crc)`.

---

## Known limitations

- `SOROUSH_CAPTURE_FINAL_BYTECODE=1` adds memory overhead proportional to the
  number of loaded classes and their bytecode sizes. For a Spring Boot run, this
  can be several hundred MB in aggregate across 8,000+ classes.
- The original bytes are captured from the `ClassFileStream`. If JVMTI agents
  have already transformed the bytes before the factory runs, the "original" bytes
  are post-JVMTI-transform, not the on-disk classfile bytes.
- Classfile redefinition (JVMTI redefineClasses) is not tracked — the artifact
  reflects the first load, not subsequent redefinitions.
